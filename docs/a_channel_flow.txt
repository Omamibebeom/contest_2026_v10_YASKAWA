//==============================================================================
// a_channel_flow.txt —— a 通道 (放置板物件): 安川 job 的步驟、輸入解碼表、時序
//
// 本文件所有數字都來自樹莓派端程式, 改程式就要同步改這裡:
//   3-bit 編碼表 / 失敗碼 / 保持秒數  → pi_gpio_controller.py 頂端 IO_CODES、FAIL_CODE、HOLD_SEC、FAIL_HOLD_SEC
//   辨識 (投票) 秒數                    → main_contest.py 的 VOTE_SEC
//   起始姿態與電爪開合一次              → 題目卷「評分規範」(2026 題目卷出來後請再對一次)
//
// a 通道只判斷【顏色】, 不判斷形狀。
// ※ 本檔只描述每一步「要做什麼」; job 的 INFORM 語法請以 YRC1000 作業指令手冊為準。
//==============================================================================


//===== 賽前接線 (樹莓派側 BCM 編號, 見 pi_gpio_controller.py; 安川側編號依現場配線, 接好後記下) =====
//   安川通用輸出     ──▶ 樹莓派 GPIO26   (ready: 通知樹莓派開始辨識)
//   樹莓派 R1 (17)   ──▶ 安川通用輸入 ①  (觸發: 編碼有效, 保持 HOLD_SEC = 7 秒)
//   樹莓派 R2 (27)   ──▶ 安川通用輸入 ②  ┐
//   樹莓派 R3 (22)   ──▶ 安川通用輸入 ③  ├ 3-bit 顏色編碼
//   樹莓派 R4 (23)   ──▶ 安川通用輸入 ④  ┘
//   光電感測器       ──▶ 安川通用輸入 ⑤  (深度, 不經樹莓派; 題目沒有深度判斷就不用接)


//===== 輸入解碼表 (預設值; 選手若改了 IO_CODES / FAIL_CODE, 這張表要跟著改) =====
//    ①    ②  ③  ④    意義
//    1     0   0   1    red
//    1     0   1   0    blue
//    1     0   1   1    green
//    0     1   1   1    【辨識失敗】① 不會變高, job 靠等待逾時後讀 ②③④ 得知
//    0     0   0   0    待命 / 訊號已收回
//
//   ※ 失敗碼 1 1 1 是 IO_CODES 沒用到的組合, 所以就算 ① 那條線接觸不良,
//     也不會把某個顏色誤讀成失敗。新增顏色時不要用 1 1 1。


//===== 時序 (以手臂拉高 ready 的瞬間為 t = 0) =====
//   樹莓派: t=0 開始投票 VOTE_SEC = 3 秒 (每一幀看到的最大物件顏色投一票)
//   成功: t=3 先擺好 ②③④ → t=4 ① 拉高 → 保持 HOLD_SEC = 7 秒 → t=11 全部關閉
//   失敗: t=3 ②③④ = 1 1 1, ① 不拉高 → 保持 FAIL_HOLD_SEC = 10 秒 → t=13 全部關閉
//
//   job 等待 ① 的逾時設 8 秒:
//     成功時 t=4 就通過; 失敗時 t=8 逾時, 此時失敗碼還在 (到 t=13), 讀 ②③④ = 1 1 1 即知失敗。
//   不可設 15 秒: 失敗碼 t=13 已收回, 逾時後只讀到全 0, 分不出「失敗」和「樹莓派沒回應」。


//===== 每一件 a 物件的 job 步驟 =====
//
//  ┌ 1. 移到題目區 2 的該物件夾取點 (預教點位)
//  ├ 2. 關夾爪; 稍等 (約 0.3 秒) 讓夾爪確實夾住
//  ├ 3. 移到【固定檢測位】
//  │    ※ 此點要讓物件完整入鏡且夠大 (面積要超過該顏色 profile 的 min_area)
//  │    ※ 教這個點位時, 樹莓派同時跑 io_test.py 看畫面, 直到出現綠框、左上角 seen= 顯示正確顏色
//  ├ 4. 接 GPIO26 的通用輸出 = 1 (拉高 ready)   → 樹莓派終端印「[a] 收到 ready, 投票 3 秒」
//  ├ 5. 等通用輸入 ① == 1, 逾時 8 秒 (理由見上面「時序」)
//  ├ 6. ① == 1 的 7 秒窗內讀 ②、③、④ → 三個顏色分支 (可巢狀判斷: 先看 ②, 再 ③, 再 ④)
//  ├ 6-1. 逾時的那條分支: 讀 ② ③ ④
//  │    == 1 1 1 → 辨識失敗: 建議把物件稍微轉個角度 / 重新對正鏡頭後, 回到第 4 步再試; 或放到暫置區跳過。
//  │    == 0 0 0 → 樹莓派沒有回應: 檢查 main_contest.py 是否還在跑、通用輸出 → GPIO26 接線。
//  ├ 7. 讀光電感測器那路輸入 → 深度分支 (題目沒有深度判斷就省略本步)
//  ├ 8. 接 GPIO26 的通用輸出 = 0 (放下 ready)
//  │    ※ 不可省略: 樹莓派要看到 ready 回到 0 (WAIT_RELEASE 狀態) 才會接受下一件的觸發
//  ├ 9. 依顏色 (和深度) → 移到題目區 3 對應點位
//  └ 10. 開夾爪, 抬起離開
//
//  → 回到主流程, 接下一件 (下一件是 b 就走 yaskawa_job_interface.txt 的流程)


//===== 整體 flow 範例 (假設題目要求 5 件: a, b, b, a, b) =====
//
//   Start
//    ├─ 起始姿態 + 電爪開合一次            (題目卷評分規範)
//    ├─ 第 1 件 ── a 子流程 (上面 1~10 步)
//    ├─ 第 2 件 ── b 子流程 (yaskawa_job_interface.txt 第三節)
//    ├─ 第 3 件 ── b 子流程
//    ├─ 第 4 件 ── a 子流程
//    ├─ 第 5 件 ── b 子流程
//    └─ 回起始姿態
//
//   b 通道的夾取順序寫在 main_contest.py 的 PICK_ORDER; 用完會回 B003=1。
//   a 與 b 的先後由 job 的排列決定。


//===== 賽前用 io_test.py 驗接線 (樹莓派端, 手臂不必先接好流程) =====
//   python3 io_test.py
//   1~9  送出 IO_CODES 裡第 1~9 個顏色的訊號 (預設 1=red 2=blue 3=green; 不看相機, 純測接線)
//   f    送出失敗碼 (① 不拉高, ②③④ = 1 1 1)
//   0    全部繼電器關閉
//   r    把相機目前看到的顏色送出去 (和比賽動作一樣)
//   q    離開
//   畫面左上角: seen = 目前看到的顏色, ready = GPIO26 電位, last IO = 最後送出的訊號
//   對照安川的輸入監看畫面與上面的解碼表。


//===== 常見問題 =====
//
// Q: 等通用輸入 ① 一直等不到?
// A: 看樹莓派終端有沒有印「[a] 收到 ready」。
//    沒印 → 通用輸出到 GPIO26 的接線或電位有問題 (跑 io_test.py, 左上角 ready= 會即時顯示)。
//    有印但送了失敗碼 → 終端會印「沒看到任何 IO_CODES 裡的顏色」: 物件太小 (min_area)、
//    HSV 沒調好, 或顏色名和 IO_CODES 對不上。
//
// Q: 判到錯的顏色?
// A: 兩個顏色的 HSV 範圍重疊。用 vision_tuner.py 依現場燈光重調 (按 n 切換已存顏色),
//    再用 io_test.py 確認 seen= 顯示正確。
//
// Q: 逾時後讀到 ②③④ 全是 0?
// A: 等待的逾時設太長, 失敗碼已經收回。改成 8 秒。
